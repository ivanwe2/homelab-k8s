# Design decisions

The main choices in this cluster, why I made them, and what each one costs.

| # | Decision | Why | Trade-off / alternatives |
|---|---|---|---|
| 1 | **k3s on 3 VMs** (1 server, 2 agents) on one Proxmox host | k3s is a full, certified Kubernetes distribution in one binary, with ingress, load balancer and storage built in. Three nodes make scheduling, draining and node failure observable. | Not real high availability: one physical host and one control-plane node. kubeadm or Talos would teach more cluster operations at the cost of setup time. |
| 2 | **VMs, not LXC containers** | Kubernetes needs kernel modules and capabilities that unprivileged LXC containers don't provide. | VMs use more RAM than containers. |
| 3 | **Pull-based GitOps with Argo CD** | No CI system needs cluster credentials. Manual drift is reverted automatically. Git history is the audit log, and a rollback is a `git revert`. Argo CD's UI makes sync state and drift visible. | Flux is lighter, but has no built-in UI. |
| 4 | **App-of-apps** | Only one Application (`root`) is applied by hand. Deploying an app means adding a file to `apps/`. | ApplicationSets would generate Applications from templates. Unnecessary at this size. |
| 5 | **Argo CD installed by Helm, not self-managed (yet)** | Self-management is tidy, but syncs can fight with values Argo CD writes at runtime (for example the admin password). The Helm values still live in Git. | Argo CD upgrades are a manual `helm upgrade`. |
| 6 | **Automated sync with prune, self-heal and retry (refresh on)** | Git is the only way to change the cluster. Deleted files get cleaned up. Transient failures retry, and a fix commit is picked up while retrying. | A bad commit is applied immediately, so validation happens before pushing (`kubectl apply --dry-run=server`). |
| 7 | **Pinned chart and image versions** | Rebuilding the cluster produces exactly the same result, and upgrades are deliberate commits. | Upgrades are manual. |
| 8 | **Sealed Secrets** | Simplest way to keep secrets in Git: encrypt with a public key, decrypt only inside the cluster. No external secret store needed. | The private key must be backed up, or a rebuilt cluster can't read existing secrets. SOPS or External Secrets (with Azure Key Vault, for example) are the usual alternatives at larger scale. |
| 9 | **Private root CA via cert-manager**, names under `*.homelab.internal` | Trusted HTTPS everywhere without owning a domain or exposing anything to the internet. `.internal` is reserved for private use. | Each client must trust the CA once. Switching to Let's Encrypt later only means changing the issuer. |
| 10 | **TLS terminated at Traefik** | One place handles certificates for every app; services inside the cluster speak plain HTTP. | Traffic inside the cluster isn't encrypted (acceptable in a single-host lab). |
| 11 | **local-path storage** | Built into k3s and fast. Replicated storage brings no real safety on a single physical disk. | A volume is pinned to one node: if that node is unavailable, its pod can't move (shown in a drill, lessons-learned #6). Stateful apps get availability from their own replication instead; Longhorn stays an option for apps that can't replicate. |
| 12 | **Memory limits, no CPU limits** | Exceeding a memory limit kills only the offending container, protecting the node. CPU limits throttle apps that would otherwise run fine; CPU *requests* still reserve capacity for scheduling. | A CPU-hungry pod can use spare CPU on its node. |
| 13 | **No Bitnami charts or images** | Broadcom ended the free Bitnami image catalog in August 2025. Charts depending on it break or freeze. | Use upstream charts and operators instead (for example CloudNativePG for PostgreSQL). |
| 14 | **kube-prometheus-stack, trimmed for k3s** | The standard Prometheus and Grafana bundle, with the operator and ready-made dashboards. k3s runs the controller manager, scheduler, proxy and datastore inside one process, so those scrape targets are disabled instead of showing as permanently down. No Alertmanager yet, 3-day retention, 1 GiB memory limit. | No alerting yet, and k3s internals aren't scraped individually. VictoriaMetrics would use less memory, but Prometheus is what the thesis and most employers use. |
| 15 | **Prometheus scrapes every ServiceMonitor in the cluster** | By default it only picks up monitors labelled for its own Helm release. Turning that off means any app that ships a ServiceMonitor is scraped with no change to the monitoring config. | In a shared cluster, any team's monitor would be picked up too. Fine for one owner. |
| 16 | **App config as a Kustomize-generated ConfigMap with a content hash** (Glance) | Any config change produces a new ConfigMap name, so the Deployment rolls out. The change is visible in Argo CD, a broken config fails the rollout instead of being quietly ignored, and reverting the commit restores the exact previous version. | Every config change restarts the pod. The alternative, letting the app hot-reload a mounted file, avoids the restart but can leave Git and the running config silently disagreeing. |
| 17 | **Private IP addresses are fine in a public repo; credentials never are** | `192.168.x.x` addresses aren't reachable from the internet and reveal little. Dashboard configs reference them openly, while anything that grants access (tokens, passwords) goes through Sealed Secrets or isn't used at all. | Someone reading the repo learns the shape of my home network. |
| 18 | **Static IPs below `.100`, DHCP pool `.100` to `.199`** | The router's DHCP pool used to overlap the static addresses, which caused a real IP conflict (lessons-learned #7). Separate ranges make that impossible. | Static addresses are tracked by hand. |
| 19 | **PostgreSQL through the CloudNativePG operator**, 2 instances on local-path | The operator does what a DBA would: creates the instances, sets up streaming replication, generates credentials and promotes the replica when the primary fails. Each instance keeps its own copy on its own node, so the database survives a node loss without replicated storage. | Another operator and its CRDs to keep upgraded. Its CRDs must never be deleted: removing the `Cluster` type deletes every database cluster with it. |
| 20 | **Postgres image pinned to minor version, variant and OS** (`17.11-standard-trixie`) | Major upgrades change the on-disk format and need a deliberate migration; minor upgrades are a one-line commit that the operator rolls out replica first, then switches over. The plain `:17` tags older guides use are no longer published. | Minor upgrades are manual commits, not automatic. |
| 21 | **Valkey instead of Redis**, as a plain Deployment without persistence | Valkey is the Linux Foundation fork of Redis (created after Redis changed its license in 2024) and speaks the same protocol. Nextcloud only uses it for caching and file locks, which are rebuilt instantly after a restart, so there's nothing to persist. | One replica: while it restarts, Nextcloud runs without its cache and locking. |
| 22 | **Generated database credentials stay inside the cluster** | CloudNativePG writes the app user's password into a Secret, and Nextcloud reads it from there. That credential never exists on a laptop, in shell history or in Git. | Reading it requires cluster access. A rebuilt cluster gets a new password, which is fine because the app reads it from the same Secret. |
| 23 | **Version upgrades through pull requests** | Argo CD follows `main` only, so nothing deploys until a reviewed PR is merged. Nextcloud can't be downgraded or skip a major version, so its upgrades are one-way doors that deserve a review step and a written reason. | Slower than committing to `main`. For a one-person repo the review is self-review, but the record is still worth it. |
| 24 | **Nextcloud's files on a single local-path volume** (accepted for now) | The database is replicated; the files are not. Replicating them needs distributed storage (Longhorn) or object storage as Nextcloud's primary storage, both significant extra moving parts on what is physically one disk. | If the node holding the volume is down, Nextcloud is down until it returns. Off-machine backups are the planned mitigation. |
